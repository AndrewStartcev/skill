# Handoff: Figma → разработка → WordPress/Bitrix

## Что передать
1. Ссылку на актуальный Figma-файл/фреймы, статус Ready for dev, дату и историю решений.
2. Design tokens: color, typography, spacing, radius, shadow, breakpoints, motion; mapping к CSS custom properties/SCSS.
3. Компоненты: назначение, свойства/variants, интерактивные состояния, ограничения и правила композиции.
4. Страницы: desktop/mobile и промежуточные ширины, content max-width, grid, sticky, overflow, z-index, responsive behavior.
5. Тексты: финальные версии, Title/description/H1, alt, FAQ, тексты ошибок, статусы согласования, URL/перелинковка.
6. Изображения/иконки: лицензии, исходники, форматы, crop, aspect ratio, responsive sizes, декоративность.
7. Поведение: формы, валидация, отправка, успех/ошибка, модальные окна, меню, поиск, фильтры, пагинация, доступность.
8. SEO: canonical, robots, schema, breadcrumbs, карта URL и 301 для редизайна, sitemap, HTML-доступность основного контента.
9. Аналитика: события, названия целей, места вызова, критерии корректной отправки; без передачи секретов.
10. QA: тестовые сценарии, матрица устройств, критерии приемки, ответственные.

## Реализация
- HTML: семантические header/nav/main/section/article/footer, корректная иерархия headings, реальные a[href] для ссылок и button для действий.
- CSS: mobile-first где уместно, BEM или согласованная методология, компоненты и токены, container queries/media queries по реальному поведению контента.
- JS: progressive enhancement, управление фокусом, доступные раскрытия, формы без скрытых зависимостей; избегать ненужных тяжелых библиотек.
- WordPress: Gutenberg blocks/ACF или кастомные шаблоны по архитектуре проекта; SEO-поля управляются явно, редактор не должен ломать макет длинным контентом.
- Bitrix: шаблоны компонентов, инфоблоки/HL-блоки по задаче, контролируемые метаполя и свойства; не дублировать SEO-логику между шаблоном и CMS.
- Изображения: современные форматы при поддержке, width/height или aspect-ratio, responsive srcset/sizes, lazy-load ниже первого экрана, не откладывать LCP-изображение без оснований.
- Шрифты: проверенные лицензии, кириллица, subset/woff2 при применимости, font-display и предотвращение CLS.
- Performance: ориентиры полевых Core Web Vitals — LCP ≤2.5 с, INP ≤200 мс, CLS ≤0.1 на 75-м перцентиле. Не считай Lighthouse заменой полевых данных.
- Доступность: проверка WCAG 2.2 AA в браузере, не только в Figma.

## Карта соответствия компонентов
| Figma | Frontend | CMS-данные | Состояния | QA |
| --- | --- | --- | --- | --- |
| Button/Primary | .button.button--primary | текст CTA + URL/действие | focus, disabled, loading | клавиатура, контраст |
| ServiceCard | .service-card | название, описание, ссылка, изображение | длинный текст, нет фото | overflow, alt |
| Accordion/FAQ | details/summary либо доступный JS | вопрос, ответ | open, closed | keyboard, HTML |
| LeadForm | .lead-form | поля/валидация/согласие | error, success | отправка, цель |

Это пример; подстраивай под существующий код и систему именования.

## Особенности согласования
- Не заменяй недостающие требования догадками: фиксируй вопросы и владельца решения.
- Отдельно отмечай изменения, затрагивающие SEO-URL, содержание, индексацию, скорость, формы и метрики.
- Для контента зафиксируй источник истины: Figma как макет, CMS как публикуемое содержимое, матрица как редакторское согласование — без расхождений версий.
- Используй Dev Mode при наличии доступа, но не требуй его там, где достаточно аннотаций и спецификаций.
