# Skills Library

Библиотека переиспользуемых навыков (skills) для ИИ-ассистентов. Скиллы содержат общие инструкции, справочные материалы и вспомогательные инструменты. Репозиторий не привязан к конкретным клиентам, сайтам или внутренним проектам.

## Разделы

- [WordPress](./WordPress/) — разработка, архитектура, интеграции и сопровождение WordPress.
- [Frontend](./Frontend/) — HTML, CSS, JavaScript, UI-компоненты, адаптивность и доступность.
- [Design](./Design/) — веб-дизайн в Figma, UX/UI, редизайн, дизайн-системы и SEO-контент.
- [SEO](./SEO/) — техническое SEO, структурированные данные, аудит и оптимизация.
- [Kwork](./Kwork/) — оформление услуг, предложений, портфолио и рабочих процессов.

## Единая структура скилла

Каждый скилл размещается в **отдельной папке с собственным названием** внутри подходящего раздела. Название папки — в формате `kebab-case` (латиница, строчные буквы, дефисы).

```text
<Категория>/
└── skill-name/
    ├── SKILL.md
    ├── references/
    ├── scripts/
    └── assets/
```

| Элемент | Назначение |
| --- | --- |
| `SKILL.md` | Краткие, однозначные инструкции: назначение, условия применения, входные данные, порядок работы, проверка результата. |
| `references/` | Подробная документация, спецификации, чек-листы, примеры и ссылки на источники. |
| `scripts/` | Готовые скрипты и инструменты автоматизации с инструкциями по запуску. |
| `assets/` | Шаблоны, заготовки и другие необходимые ресурсы. |

Четыре элемента структуры предусмотрены для **каждого** скилла. Пока вспомогательная папка не содержит материалов, допускается сохранить в ней `.gitkeep`, поскольку Git не отслеживает пустые директории. Не создавай фиктивные инструкции или файлы ради заполнения структуры.

## Требования к SKILL.md

1. Начинай файл с YAML frontmatter: `name` и `description`. В `description` укажи, **когда** применять скилл.
2. Пиши коротко и по делу. Основные шаги, ограничения, критерии готовности и ожидаемый результат должны быть в `SKILL.md`.
3. Объёмные объяснения и примеры выноси в `references/`, а исполняемые решения — в `scripts/`. Ссылайся на них относительными путями.
4. Не дублируй общие сведения, которые не помогают выполнить задачу. Указывай проверяемые требования вместо размытых советов.
5. Делай инструкции универсальными: никаких конкретных клиентов, доменов, доступов или внутренних договорённостей.
6. Перед публикацией проверь скилл на реальной типовой задаче, устрани неточности и обнови документацию.

Минимальный шаблон:

```markdown
---
name: skill-name
description: Что делает скилл и в каких ситуациях его применять.
---

# Название скилла

## Когда использовать
Краткое описание применимости.

## Входные данные
Что требуется для выполнения задачи.

## Порядок работы
1. Действие.
2. Действие.
3. Проверка результата.

## Критерии готовности
Как определить, что задача выполнена корректно.

## Дополнительные материалы
- [Справка](references/guide.md)
```

Ссылки в шаблоне нужно адаптировать к реально существующим файлам.

## Как создавать и обновлять скиллы

1. Изучи задачу и актуальную официальную документацию. При необходимости проведи отдельное исследование.
2. Отдели универсальные правила от частных решений; проверь источники и актуальность рекомендаций.
3. Создай каталог `<Категория>/<skill-name>/` и положи в него `SKILL.md`, `references/`, `scripts/`, `assets/`.
4. Добавь проверяемые инструкции, примеры и инструменты, не загромождая основной файл.
5. Протестируй скилл на типовом сценарии и проверь итоговый результат.
6. При изменении технологий, API или стандартов пересматривай инструкции, ссылки и скрипты.

## Безопасность и конфиденциальность

**Никогда не сохраняй в репозитории:**

- API-ключи, токены, пароли, cookie, session ID, приватные ключи и любые другие секреты.
- Файлы `.env` с реальными значениями, дампы БД, резервные копии, логи с персональными сведениями.
- Персональные данные, клиентские материалы и закрытую информацию.
- Реальные адреса административных панелей, внутренние URL и специфичные настройки отдельных проектов.

Для демонстрации используй только **вымышленные данные** и безопасные заглушки (`example.com`, `YOUR_API_KEY`). Если скрипту нужны секреты, получай их из переменных окружения или внешнего защищённого хранилища; не фиксируй значения в Git.

Перед каждым коммитом проверяй изменённые файлы на секреты и приватные сведения. `.gitignore` — дополнительная защита, а не замена проверке.

## Принципы

- Универсальность и переиспользование.
- Краткие инструкции, подробности по ссылкам.
- Проверяемость и воспроизводимость результата.
- Минимум зависимостей и лишней сложности.
- Актуальность источников, тестирование и безопасное использование.
